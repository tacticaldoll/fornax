# Source conversation (the material to report on)

**User**: 我們有一條寫在治理文件裡的慣例，說「新增檢查前要先說它會擋下什麼」。這條從來沒有被任何機制強制過，只是寫在那裡。要不要把它變成一個真的檢查？

**Assistant**: 先問一件事 —— 這條慣例被違反過嗎？

**User**: 查了，沒有。每次有人加檢查，都有在 commit message 裡說理由。

**Assistant**: 那這個檢查會擋下什麼？如果答案是「到目前為止什麼都沒有」，那它的綠燈就不代表任何事，而讀的人會以為它代表什麼。

**User**: 但未來可能有人忘記。

**Assistant**: 可能。問題是成本：這個檢查要判斷「理由充不充分」，那不是機器能答的，所以它只能檢查「有沒有寫一段字」。有人會寫一段字然後照樣加沒用的檢查，而檢查會過。我們就買到一個只擋得住「完全不寫」的東西，代價是每次改動都多一個要應付的關卡，加上它自己會生出關於它自己的討論。

**User**: 那不如就留在文件裡。

**Assistant**: 我同意，而且我想把理由寫下來：一個從沒發生過的失敗，配上一個只能檢查形式的檢查，比單獨的寫作規則更糟 —— 它花掉同樣的注意力，而它的綠燈意義比讀者以為的少。真正該記下來的是「加檢查前先說它會擋下什麼，以及它每次改動的成本」，那是判斷，不是檢查。

**User**: 那如果以後真的有人違反呢？

**Assistant**: 那時候就有一個具體的失敗可以指，而那正是決定要不要買這個檢查所需要的證據。現在沒有，所以現在不買。
